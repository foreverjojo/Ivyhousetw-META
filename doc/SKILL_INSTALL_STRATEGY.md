# Skill 安裝策略（Repo-based）

本文件說明本專案的 Skill 安裝策略：所有可執行的 Skills（含 `SKILL.md` 與相關腳本）一律安裝與維護在專案目錄 `/.agent/skills/` 下，並納入版本控制與團隊協作流程。

## 目標

- 讓團隊以相同版本的 Skills 進行開發與審查，降低「不同人本機不同技能版本」造成的結果差異。
- 讓 Skills 的引入流程可追溯、可審計、可回滾，降低供應鏈風險。
- 讓 Skills 可在 CI / 本機環境中一致重現與驗證。

## 為什麼採用 `/.agent/skills/`（Repo-based）？

- 版本控制：Skills 與專案程式碼一起進 Git，任何變更都有 commit 記錄與可追溯來源。
- 安全掃描：可在合併前進行靜態掃描（例如檔案權限、可疑系統呼叫、網路存取、危險指令特徵）。
- 團隊共享：新人 clone 專案即可取得一致的 Skills，不需要額外的個人安裝步驟。
- Code Review：以 PR 的方式審核 Skills 變更，避免未審核的遠端程式碼直接進入工作流。
- 可重現性：同一版專案對應同一版 Skills，便於除錯與回歸驗證。

## 安全機制（必備）

### 1) 來源白名單（Allowlist）

- 僅允許從明確列出的來源（組織/Repo）取得 Skills。
- 禁止從未知來源或臨時分享連結直接匯入可執行腳本。

### 2) Skill Manifest（可追溯資訊）

每次引入或更新 Skills 時，必須在專案內留下可審計的資訊（可用 JSON/YAML 形式），至少包含：

- 來源 Repo/URL
- 來源 commit hash / tag / release 版本
- 下載時間與操作者
- 檔案清單與雜湊（例如 SHA-256）
- 轉換與掃描結果摘要

### 3) 審計紀錄（Audit Log）

- 任何「下載、轉換、安裝、更新」行為都應留下可查詢紀錄（檔案或 history），以便追蹤風險與回溯問題。

### 4) 可回滾（Rollback）

- Skills 的變更必須可透過 Git 回退到任一已知穩定版本。
- 若 Skills 由自動流程取得，需保留「上一版可用快照」以快速復原。

### 5) 權限與執行邊界

- Skills 執行應採最小權限原則：預設不可連網、不可寫入非專案指定路徑、不可執行危險系統指令。
- 需要連網或寫入時，必須以明確的授權機制（例如人工批准）進行。

## 團隊工作方式（建議）

- Skills 變更以 PR 進行，至少一位維護者審核後才能合併。
- 每次合併後由 CI 執行基本檢查（語法、靜態掃描、關鍵測試）以降低回歸風險。
